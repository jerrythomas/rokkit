# @rokkit/graph

Node-link diagram components for Svelte 5. ER diagrams, schema entity tables and dependency /
call graphs from one component, driven by field-mapped data rather than a fixed schema type.

Extracted from dbd's ER viewer and rebuilt data-first. The package has no opinion about
databases: it knows nodes, edges, groups and kinds. The dbd vocabulary lives entirely in the
optional `./schema` entry point.

## Install

```bash
npm install @rokkit/graph
```

`@rokkit/ui` and `svelte` are **peer** dependencies. `@rokkit/ui` is optional — only the
`./schema` views use it — so a consumer that wants the canvas alone does not pull it in.

## Entry points

| Import | Contains |
|--------|----------|
| `@rokkit/graph` | `Graph`, `GraphState`, layouts, presets, the normalizer, icons, types |
| `@rokkit/graph/schema` | ER-flavoured views and the dbd adapter: `EntityView`, `EntitiesView`, `NoteBlocks`, `fromSchemaModel`, `toGraphInput`, `SCHEMA_FIELDS`, `DEPS_FIELDS` |
| `@rokkit/graph/icons` | `DEFAULT_ICONS` alone, with no Svelte imports — for a UnoCSS safelist, which Node loads |

## The data contract

`nodes` and `edges` are whatever shape you already have. `fields` maps dotted paths from that
shape to the canonical model, resolved **once**, before anything else runs. Nothing downstream
sees your field names.

```js
const fields = {
  id: 'key',          // explicit id — see the warning below
  label: 'key',
  group: 'team',      // clusters, and the group colour ramp
  kind: 'type',       // data-node-kind, for CSS
  rows: 'endpoints',
  rowName: 'label',
  rowBadges: { pk: 'primary' },
  source: 'caller',
  target: 'callee'
}
```

Anything omitted falls back to the same-named key, so a source already shaped like the
canonical model needs no map at all.

**Give nodes an explicit `id` if you ever intend to regroup.** `id` defaults to
`${group}.${label}`, so switching `group` from `schema` to `kind` silently re-keys every node
and every edge stops resolving.

## Canonical model

```ts
type GraphNode = {
  id: string
  label: string
  group?: string     // open vocabulary — a schema, a team, a package
  kind?: string      // table | view | matview | materialized_view | function | procedure | trigger | enum
  rows: GraphRow[]
  note?: string
  meta: Record<string, unknown>   // source fields the map did not claim
}

type GraphEdge = {
  id: string
  source: string
  target: string
  sourceRow?: string
  targetRow?: string
  kind: 'reference' | 'dependency'   // what layouts branch on
  relation?: string                  // the producer's own verb: reads | writes | calls | member
  cardinality?: string
  action?: string
  unplaced?: 'source' | 'target' | 'both'
}
```

### An unplaced edge is dimmed, never dropped

An endpoint the map cannot resolve is a **normal state at scale**, not a defect. Sensei's code
graph reports 59.6% of 4.08M edges with a null target: the call is real, the callee is simply
not indexed. Dropping those makes the graph look far more complete than it is, so the edge is
kept, the raw value stays readable on `source`/`target`, and `unplaced` records which end.

## Layouts

A layout is a pure `(model, options) => LayoutResult` — DOM-free, synchronous, deterministic.
Your own slots in exactly the same way.

| Name | Shape | For |
|------|-------|-----|
| `flow` | Cards in columns by reference direction | **The default.** Every edge leaves right, enters left |
| `cluster` | Cards in group boxes | Entity diagrams grouped by schema |
| `neighborhood` | One focus node + its 1-hop neighbours | Walking a graph one step at a time |
| `radial` | A tidy tree or dendrogram around a circle | Call graphs — who calls whom, and how deep |
| `points` | Degree-sized rounded rects, shelf-packed | Dense graphs — a code index, 1000+ nodes |
| `world` | Nested rectangles, area proportional to a measure | Containment — where the mass of a codebase is |
| `sunburst` | Nested wedges, angle proportional to a measure | The same containment, with depth on the radius |
| `structure` | Radial dendrogram + bundled edges | A codebase: containment on the rim, calls drawn through it |

```js
import {
  cluster, flow, neighborhood, points, radial, structure, sunburst, world, layouts
} from '@rokkit/graph'
```

### Options

| Option | Default | Effect |
|--------|---------|--------|
| `density` | `'keys'` | `names` \| `keys` \| `full` — how much of a node's row list a card shows |
| `arrange` | `'untangle'` | Cluster ordering. `untangle` chains heavily-linked groups; `a-z` is area-descending |
| `groupBy` | `'group'` | Outer grouping axis — `group` or `kind` |
| `nestBy` | — | Subdivide each cluster by a second axis. Omit for one level |
| `edgeStyle` | `'curved'` | `curved` \| `orthogonal` |
| `focus` | — | `neighborhood` only — the node to centre |
| `depth` | `1` | `neighborhood` only — how many hops out from the focus |
| `sizeBy` | `'degree'` | `points` / `world` — the measure area encodes |
| `sizeScale` | `'linear'` | `points` only — `log` for a measure spanning orders of magnitude |
| `focusPath` | `[]` | `world` / `sunburst` — the subtree to render as the whole canvas |
| `levels` | `2` | `world` / `sunburst` — how many levels below the focus to materialise |
| `radialMode` | `'tree'` | `radial` only — `tree` reads radius as depth, `dendrogram` pins leaves to the rim |
| `bundleTension` | `0.85` | `structure` only — how hard edges are pulled onto the tree. 0 is a straight chord |
| `groupTint` | `false` | Paint each card with its group's ramp — schema without cluster boxes |
| `expanded` | — | Node ids shown at full detail whatever `density` says |

### Two-level clustering

Schema is the right axis for an ER diagram and a poor one for a dependency graph, where one
schema holds a table, a trigger and a procedure. `nestBy` shows both facts at once:

```svelte
<Graph {nodes} {edges} {fields} groupBy="group" nestBy="kind" />
```

Clusters come back as a FLAT list with `depth` (0 outer, 1 inner) and `parent`. They are
absolutely positioned, so every outer box is emitted first and paint order does the nesting —
there is no DOM tree. Passing the same axis for both is ignored, not rendered: a box
subdivided by itself yields one child holding everything.

### `flow` — direction you can read, links you can trace

Raised from an ER diagram where connectors were buried behind entities: **5 of 9 edges passed
over a card that was not one of their endpoints.**

`cluster` picks a connector's side by relative POSITION, so an edge's exit side tells a reader
where the other box happens to sit, not which way the reference points. `flow` ranks nodes by
reference direction — the referenced table sits right of the one referencing it — and then
every edge leaves the **right** and enters the **left**, unconditionally.

Those are one feature, not two. Fixed ports on a schema-grouped arrangement make burial worse:
a right-exit connector reaching a left-hand table has to sweep out and back across everything
between. Ranking is what makes x-position mean direction, and only then are fixed ports honest.

Cycles — a real schema has mutual foreign keys — are broken for ranking, kept for drawing, and
marked `back` on the routed edge so a theme can distinguish the one connector that doubles back.

`flow` emits **no clusters**: ranking and schema grouping compete for the same axis, and a box
cannot be both "in the `public` box" and "in column 3". `cluster` remains the schema view.

**What it does not do yet:** a long edge is still drawn straight over any box between its
endpoints. Routing around needs dummy nodes on the intervening ranks, which is its own slice.

### `radial` — a call graph has a shape

`points` shelf-packs a call graph into group boxes. At seven services that already reads as a
stack: tiny rects with each label colliding with the row beneath. Packing answers "how much is
there"; a call graph asks "who calls whom, and how deep does it go", which is a SHAPE.

Angle separates the subtrees, radius carries the depth. Two modes:

```svelte
<Graph {nodes} {edges} layout="radial" />                      <!-- radius = depth -->
<Graph {nodes} {edges} layout="radial" radialMode="dendrogram" /> <!-- leaves on the rim -->
```

**A call graph is not a tree**, and the layout does not pretend otherwise. A spanning tree
picks one parent per node — breadth-first, so a node sits at its shortest distance from a root
— and every edge it could not use is still drawn, marked `back`. "b also calls this" is exactly
what a reader is looking for, and a tree that drops half its edges looks complete while being a
quarter of one. Cycles terminate because a claimed node is never re-claimed; a disconnected
node becomes its own root rather than vanishing.

### `structure` — a codebase, and the calls drawn through it

The view `radial` cannot be over a real repo. A call graph's own spanning tree has hundreds of
roots, so capping its depth prunes almost nothing and the rim comes out a grey smear. A
codebase's structure is CONTAINMENT — crate, module, file — and that is a real tree with one
root, which is what makes "show two levels, then drill" mean something.

So the hierarchy is `buildTree` over `path`, the same tree `world` and `sunburst` use, and the
calls are drawn ON it rather than defining it:

- every **leaf** sits on one rim, so leaves are comparable and the rim can hold labels
- each ancestor level gets an **arc** outside that rim, naming the region under it
- an **edge** routes up to its two ends' lowest common ancestor and back down, then relaxes
  toward the straight chord by `bundleTension`

```svelte
<StructureDiagram {nodes} {edges} {fields} levels={1} controls legend />
```

**`levels` decides what sits ON the rim**, which is not quite what it means for `world` and
`sunburst` — there it caps how deep the boxes nest, here it cuts the tree and everything below
the cut is aggregated into the box standing for it. Over rokkit's own source: `1` is fourteen
packages you can read, `2` is 174 modules, `3` is 435 files. A call between two files in the
same package becomes a self-link at level 1 and is dropped, so only edges that actually cross
the boundary survive — which is what makes a cut view legible rather than merely smaller.

Bundling is what makes it readable at scale — edges travelling the same way through the tree
pull together, so rokkit's own 801 imports become visible flows between packages instead of a
solid disc of ink. `bundleTension={0}` is the straight chord, which is what you switch to when
you want to follow one edge exactly.

An edge is classified by how far it travels in the tree — `local`, `crate`, `cross` — measured
against each end's own depth rather than an absolute level, because the tree folds single-child
wrappers and an absolute rule would classify the same file differently depending on how many
siblings its module happened to have.

### `sunburst` — the treemap's question, asked radially

Same tree, same measure, same captions as `world`, so the two are one dataset drawn twice:

|  | measure | depth |
|--|---------|-------|
| `world` | area | nesting you have to look for |
| `sunburst` | angle | the radius, read at a glance |

A treemap spends its pixels better; a sunburst tells you how deep the tree goes before you have
read a label. A wedge comes back as a `Cluster` carrying `wedge: { r0, r1, a0, a1 }` — numbers,
not a path string, so the layout stays DOM-free and testable to exact radians.

### The world view is boxes all the way down

`world` returns **no cards at all**. A treemap nests one shape — a box with a label and an area
— so a leaf comes back as a `Cluster` too, carrying `nodeId` and `kind` so it stays selectable
and themeable. Rendering leaves as node cards instead put a card's furniture inside a hierarchy
of label boxes, down to a row count that reads `0` for anything without rows.

A box's caption is its MEASURE, not its child count. Where area encodes a quantity, a number
beside the box reads as the thing driving its size, and a child count is a different number
that occasionally coincides.

### Applicability

Not every option reaches every layout, and a control wired to one that does not is worse than a
missing control — it moves and nothing happens, which reads as a broken view:

```js
import { appliesTo, LAYOUT_OPTIONS } from '@rokkit/graph'

appliesTo('world', 'density')  // false — a treemap box has no row list to thin
LAYOUT_OPTIONS.world           // ['sizeBy', 'focusPath', 'levels']
```

Two entries are not simply "what the layout reads": `edgeStyle` is applied when a path is
drawn, so it belongs to every layout that produces edges (`world` produces none), and
`neighborhood` takes no `density` because it builds cards at `full` unconditionally.

## Using it with dbd

`./schema` is the only place that knows dbd's vocabulary. It does **not** import dbd's
`SchemaModel` type — the hand-written mirror of `schema_model.rs` stays in the consuming app,
so this package never becomes a third definition to keep in step.

### A schema is two graphs, not one

dbd's v2 `SchemaModel` splits the database and says so in its own doc comments: `tables` is
*"Tables only"*, `refs` is *"Foreign keys only — the dependency graph is `deps`; an ER
renderer wants these and a call-graph renderer wants those."*

That is a modelling fact, not a rendering preference. **An ER diagram is table entities and
their relationships.** A view is a derived projection, a routine is behaviour; neither is an
entity, and in v2 neither even has columns — put them on an ER canvas and they render as
orphan cards with nothing in them and no edges.

```js
import { toGraphInput, fromSchemaModel } from '@rokkit/graph/schema'

const er   = toGraphInput(model, 'er')            // tables + refs
const deps = toGraphInput(model, 'dependencies')  // tables + entities, deps as edges
```

```svelte
<Graph nodes={er.nodes} edges={er.edges} fields={er.fields} />
```

Tables stay in the dependency scope because a view READS a table; dropping them would leave
every edge dangling. `er` is the default, so a caller written against v1 reads a v2 model
unchanged. `fromSchemaModel(model, { as })` is the same choice when you want a normalized
`GraphModel` rather than component props.

A `deps` edge carries dbd's verb on `data-edge-relation` (`reads`, `writes`, `calls`,
`member`) while `data-edge-kind` stays `dependency` — the coarse kind is what layouts branch
on, the verb is what you theme and label with.

## Colour: two vocabularies, deliberately split

- **Node kinds are a closed set** → plain CSS on `data-node-kind`. One rule retones one kind.
- **Groups are open-ended** → `createGraphPreset({ groups, shades, using })` assigns a ramp.

```js
import { createGraphPreset } from '@rokkit/graph'

const preset = createGraphPreset({ using: 'pattern' })  // 'color' | 'pattern'
```

There is no `kinds` map on the preset. A kind is known at build time and belongs in a
stylesheet; a group name is not and cannot.

A kind override must match the theme's specificity — `[data-node-kind='table']` is (0,1,1)
against a theme's (0,2,0) and silently loses:

```css
[data-style] [data-node-kind='table'] {
  --node-accent: var(--primary);
}
```

## Icons — you must safelist them

`DEFAULT_ICONS` maps every node kind and row badge to an `i-glyph:*` class. The component
picks one at RUNTIME from a node's kind, so those class names never appear in your source and
**UnoCSS's extractor purges them** — the icons silently vanish and every card renders a blank
box, with a perfectly correct-looking class attribute.

Safelist them from `@rokkit/graph/icons`, a subpath with no Svelte imports (a `uno.config.ts`
is loaded by Node, which cannot parse the `.svelte` the main barrel re-exports):

```js
import { DEFAULT_ICONS } from '@rokkit/graph/icons'

export default defineConfig({
  presets: [presetRokkit(config)],
  safelist: Object.values(DEFAULT_ICONS)
})
```

`presetRokkit` already exposes the `glyph` collection, so nothing else is needed. Override
per-kind through the `icons` prop to adopt a different collection:

```svelte
<Graph {nodes} {edges} icons={{ view: 'i-lucide-eye' }} />
```
