# Graphs

`@rokkit/graph` draws node-link diagrams. An ER diagram is one
thing it can draw, not what it is — the same component renders a
service call graph, a dependency tree or a lineage map, because
nothing in it knows what a table is.

See the [Graph demo](/app/graph) for a live explorer, with an ER
diagram and a service call graph rendered by the same component.

## The data contract

There is no import step and no schema type to conform to. `nodes`
and `edges` are whatever shape you already hold, and `fields` maps
dotted paths from that shape to the canonical model.

```svelte
<script>
  import { Graph } from '@rokkit/graph'

  const services = [
    { key: 'checkout', team: 'commerce', endpoints: [{ label: 'POST /cart' }] },
    { key: 'catalog', team: 'commerce', endpoints: [{ label: 'GET /products' }] }
  ]
  const calls = [{ caller: 'checkout', callee: 'catalog' }]

  const fields = {
    id: 'key',
    label: 'key',
    group: 'team',
    rows: 'endpoints',
    rowName: 'label',
    source: 'caller',
    target: 'callee'
  }
</script>

<Graph nodes={services} edges={calls} {fields} />
```

Anything omitted falls back to the same-named key, so data already
shaped like the canonical model needs no map. Fields the map does
not claim ride along on `node.meta`.

Endpoints resolve by exactly two rules: the value already IS a node
id, or it is `group.value` where the group comes from a DECLARED
path. There is deliberately no third "search the siblings" rule —
an unresolvable endpoint drops its edge rather than landing on a
coincidental match and drawing a relationship that does not exist.

## Field map

| Key                  | Reads                                         |
| -------------------- | --------------------------------------------- |
| `id`                 | stable node key (else `group.label`)          |
| `label`              | node title                                    |
| `group`              | open vocabulary — drives clustering + colour  |
| `kind`               | closed vocabulary — table/view/matview/…      |
| `rows`               | array of rows on the node                     |
| `rowName` `rowType`  | per-row name and type                         |
| `rowNote`            | per-row comment                               |
| `rowBadges`          | `{ pk, fk, uq, nn }` → truthy paths on a row  |
| `note`               | node comment (paragraphs, bullets, `code`)    |
| `source` `target`    | edge endpoints                                |
| `sourceGroup` `targetGroup` | where an endpoint's group is read from |
| `sourceRow` `targetRow`     | anchor row on each card                |
| `edgeKind`           | `reference` (default) or `dependency`         |
| `cardinality` `action`      | edge annotations                       |

## Layouts

A layout is a pure function:

```ts
type LayoutFn = (model: GraphModel, options: LayoutOptions) => LayoutResult
```

DOM-free, synchronous, deterministic — card heights come from row
counts, nothing is measured. Eight ship today — `flow` (the default:
columns ranked by reference direction), `cluster`, `neighborhood`,
`points`, `radial`, `structure`, `world` and `sunburst`. Three of them:

- `cluster` — groups become clusters, ordered to reduce edge
  crossings; each cluster's nodes are masonry-packed then flowed
  into wrapping rows. Options: `density`, `arrange`, `edgeStyle`,
  `groupBy`, `nestBy`.
- `neighborhood` — the focused node centred, nodes that reference
  it stacked left, nodes it references stacked right. Options:
  `focus` (defaults to the selection).
- `points` — a node becomes a degree-sized rounded rect,
  shelf-packed into its group. For dense graphs: a card stops
  working long before the data does, and at 1000 nodes a 248px
  card renders 11.6px wide with a 0.56px label.

Pass `layout` a name or your own function.

### Two grouping axes

Schema is the right axis for an ER diagram and a poor one for a
dependency graph, where one schema holds a table, a trigger and a
procedure. `nestBy` shows both facts at once instead of trading
one for the other:

```svelte
<Graph {nodes} {edges} {fields} groupBy="group" nestBy="kind" />
```

Clusters come back as a FLAT list carrying `depth` (0 outer, 1
inner) and `parent`. They are absolutely positioned, so every
outer box is emitted first and paint order does the nesting.

If you ever intend to regroup, give nodes an explicit `id`. It
defaults to `${group}.${label}`, so switching the axis silently
re-keys every node and every edge stops resolving.

## Edges that must not move the picture

Some edges are exactly what a reader wants to see and exactly what must not shape the layout —
files that change in the same commit with no import between them, a layering rule broken, a
suggested dependency. Let a co-change edge into `flow`'s ranking and it pulls the pair side by
side, hiding the coupling it was meant to expose. Mark it an overlay:

```js
const edges = [
  ...imports,
  { source: 'ui/components', target: 'ui/types', overlay: true, relation: 'co-change', weight: 20 }
]
```

An overlay never reaches the layout, neighbours or relationships; it is routed afterwards,
between the cards the layout placed, drawn dotted (`data-edge-overlay`), and its `weight` —
normalised to the heaviest — thickens the stroke. `fields.overlay` and `fields.edgeWeight` map
both from your own shape.

## The dependency matrix

A node-link drawing of a real codebase is a hairball. `DependencyMatrix` draws the same model as
a dependency structure matrix — every node a row and a column, a cell where the row depends on
the column — ordered providers-first, so a layered codebase is lower-triangular and **a cell
above the diagonal is a dependency against the grain**: a cycle, or a layer reaching up.

```svelte
<DependencyMatrix {nodes} {edges} {fields} groupBy="group" cell={14} />
```

`groupBy` keeps each group contiguous and outlines it on the diagonal, so a cross-module
violation is a mark outside its block. The drawing grows with the square of the node count —
aggregate files to components first; a weighted edge counts as its weight, so an aggregated
import list reads as-is. Row headers are buttons that select through `GraphState`: share one
`state` with a node-link view and both follow the same selection.

The graph demo's **Dependency matrix** and **Hidden coupling** examples read rokkit itself at
component grain — 17 of its 81 component dependencies sit above the diagonal, and 19 pairs of
components change together with no import between them.

## Three views, one state

`Graph`, `EntityView` and `EntitiesView` all read a `GraphState`.
Share one instance and selection is two-way for free.

```svelte
<script>
  import { Graph, GraphState } from '@rokkit/graph'
  import { EntityView } from '@rokkit/graph/schema'

  const state = new GraphState({ nodes, edges, fields })
</script>

<Graph {state} />
<EntityView {state} />
```

A view nested inside `<Graph>` reads the state from context. The
instance must keep STABLE IDENTITY — drive it with `update()` and
its methods rather than replacing it.

`GraphState` owns every derivation. Components render and route
intent; they compute nothing.

## Reading a large diagram

Fit-to-container alone shrinks a real schema until labels are
unreadable, so the canvas zooms:

- controls on the canvas, bottom right: `−`, the percentage
  (click to reset to fit), `+`
- ctrl/cmd + wheel — what a trackpad pinch reports as — zooms the
  diagram, not the page
- past the fit the canvas scrolls, and dragging the background pans

`zoomable={false}` turns it off; bind `zoom` to drive it yourself.

## Colour

Two vocabularies, handled differently on purpose.

Node KINDS are a closed set, so they live in CSS. Match the theme's
specificity — every style scopes its rules under `[data-style]`, so
a bare `[data-node-kind='table']` is (0,1,1) against the theme's
(0,2,0) and silently loses:

```css
[data-style] [data-node-kind='table'] {
  --node-accent: var(--primary);
}
```

Group NAMES are open — not knowable at build time. `createGraphPreset`
assigns them from a ramp, by SORTED group name so a group keeps its
colour when `arrange` reorders the layout:

```js
createGraphPreset({
  groups: ['teal', 'gold', 'violet'],
  using: 'pattern' // colour-blind- and print-safe
})
```

It resolves to CSS custom properties, not concrete fills, so an
attribute rule still wins. There is no `kinds` map on the preset:
kinds are CSS, groups are the preset.

All six styles ship a `graph.css` — base, rokkit, minimal, material,
frosted, zen-sumi.

## Using it with dbd

`@rokkit/graph/schema` carries `SCHEMA_FIELDS` and `fromSchemaModel`
for dbd-shaped JSON. It does NOT import dbd's `SchemaModel` type:
the hand-written mirror of `schema_model.rs` stays in the consuming
app, so this package never becomes a third definition to keep in
step by hand.

### A schema is two graphs, not one

dbd's v2 `SchemaModel` splits the database and says so in its own
doc comments: `tables` is "Tables only", `refs` is "Foreign keys
only — the dependency graph is `deps`; an ER renderer wants these
and a call-graph renderer wants those."

That is a modelling fact, not a rendering preference. An ER diagram
is table entities and their relationships. A view is a derived
projection and a routine is behaviour; neither is an entity, and in
v2 neither even has columns — put them on an ER canvas and they
render as orphan cards with nothing in them and no edges.

```js
import { toGraphInput } from '@rokkit/graph/schema'

const er = toGraphInput(model, 'er')             // tables + refs
const deps = toGraphInput(model, 'dependencies') // + entities, deps
```

Tables stay in the dependency scope because a view READS a table.
`er` is the default, so a caller written against v1 reads a v2
model unchanged.

A `deps` edge carries dbd's verb on `data-edge-relation` (`reads`,
`writes`, `calls`, `member`) while `data-edge-kind` stays
`dependency` — the coarse kind is what layouts branch on, the verb
is what you theme and label with.

### An unplaced edge is dimmed, never dropped

An endpoint the map cannot resolve is a normal state at scale, not
a defect. Sensei's code graph reports 59.6% of 4.08M edges with a
null target: the call is real, the callee is simply not indexed.
Dropping them makes the graph look far more complete than it is —
the most misleading thing this view can do.
